Slide 01 / 09 · Combined talk slide 1 · 75 words

ASENA

I’ll talk about two recent projects on code as policy for robotics.

The first is ASENA, which focuses on navigation. We connect a coding agent to a robot environment and explore recursive self-improvement, or RSI.

The second is Recova, which focuses on manipulation with recovery skills. Here, we use code as policy to improve learned robot policies. The goal is to make the whole loop of data collection, training, and deployment as autonomous as possible.

Slide 02 / 09 · Combined talk slide 2 · 53 words

The agent composes, the robot executes

Basically, we give a coding agent a task and observations, from either a real robot or a simulator. It writes code to control the robot, using two kinds of tools: learned policies, like VLN, and interfaces to cameras, LiDAR, and robot control. Then it looks at what happened and tries the next step.

Parallel workers evolve a shared workspace

In each pass, the agent writes code to solve the tasks. We keep the useful code as skills for the next round. The model weights stay fixed.

To scale this up, we need to collect those rollouts efficiently. So we use 16 parallel workers, each with its own simulation environment and private workspace, plus access to the navigation policy.

We distribute the tasks across the workers. After each pass, an improver agent merges, tests, and prunes their updates. That improved workspace becomes the starting point for the next pass.

This also gives us a strong starting point for future coding-agent training: the parallel environments and rollout interfaces are already in place.

The sandbox limits what generated code can do

Let me briefly explain the workspace and its safety boundaries – this is also the logic to build the robot sandbox.

The agent can write Python code, use MuJoCo, call approved model and device APIs, and reuse existing skills. It can also keep temporary files and notes.

But it cannot access raw robot controls, operator credentials, or hidden evaluation data, and it cannot modify the trusted platform.

On the real robot, the agent first proposes an action. For navigation, we check the route and obstacle clearance using LiDAR, and enforce motion limits. For generated gestures, we also validate the trajectory in MuJoCo.

The proposal then goes to an operator, who can approve or reject it and optionally give a reason. Only an approved action is passed to SONIC for execution.

The interaction layer can support an agent-training loop

Our distributed workers also give us a starting point for coding-agent training, by collecting rollouts efficiently in simulation.

For RSI, we keep the model fixed and improve the code and skills in its workspace. For training, we would use a trainable model as the sampler, then connect those rollouts and simulator-based rewards to a standard training pipeline—for example, GRPO.

So the learning mechanism is different, but much of the rollout infrastructure can be reused.

This is an important next step for us because coding policies are still slow. We’d like training to help the agent solve tasks with fewer code revisions, more effective tool calls, and better reuse of skills.

ASENA-VLN provides reusable navigation

We also developed a navigation policy called ASENA-VLN. On its own, it achieves state-of-the-art success on R2R. I won’t go into the policy details here.

What’s more interesting is what happens when a coding agent calls this policy.

The navigation tool reduces coding-agent interaction

On RxR, it improves Claude’s success rate by 11 percentage points, but lowers Astra’s by 7 points. So the effect on success depends on the model.

The efficiency benefit is much more consistent: both agents need over 50% fewer tool calls.

My takeaway is that coding agents and learned policies are complementary, especially for efficiency. The coding agent provides flexible reasoning, while the navigation policy handles movement without requiring the agent to work through every step.

Success grows as the workspace accumulates experience

This is one of the most exciting results we saw from RSI. As we run more passes and improve the workspace, success on these recurring R2R tasks reaches 98%—with the model weights completely fixed.
